# SBS_PAUSE_RESUME_FIX — подробный разбор патча

Файл объясняет, **что именно** сделал ИИ в патче `SBS_PAUSE_RESUME_FIX.patch`, **зачем** и **какие идеи** за этим стоят.

Затронуто 6 файлов:

| Файл | Суть изменения |
|---|---|
| `state/events.js` | Событие `sbs_batch` начало нести данные; добавлено `sbs_done` |
| `core/SBSoutputManager.js` | Полная переписка: замыкание → модульное состояние + управляемый таймер |
| `ui/playButtonSVG.js` | Кнопка перестала владеть логикой, стала «тупой» отрисовкой |
| `ui/runProcessControls.js` | Стала единственным местом принятия решений (start/pause/resume) |
| `visualisation/viewModes/sequenceView.js` | Подписка переехала с `collatz_done` на `sbs_batch` |
| `main.js` | Импорт `sequenceView.js` ради side-effect |

## 0. Какие баги чинились

До патча в коде было минимум **пять** независимых дефектов. Важно понимать: ИИ не «улучшал стиль», он чинил конкретные поломки.

### Баг 1 — пауза была невозможна физически

`playButtonSVG.js:5-6` переключал флаг:

```js
export function PlayOrPause() {
    SBSconfig.isRunning = !SBSconfig.isRunning;
```

А цикл в `SBSoutputManager.js:72-77` планировал следующий шаг через `setTimeout`, **не сохраняя** его идентификатор:

```js
setTimeout(() => {
    startSBS()
}, ms);
```

Идентификатор таймера выбрасывался. Даже сбросив `isRunning = false`, вы не могли отменить уже запланированный тик — он всё равно срабатывал. Проверка `if (!SBSconfig.isRunning) return;` в начале `startSBS` спасала от продолжения, но сам вызов происходил. Отменить цепочку было нечем.

### Баг 2 — возобновление с потерей позиции

Счётчик `csi` жил **в замыкании** (`SBSoutputManager.js:22`):

```js
export function SBSoutput() {
    let visibleMax = SBSconfig.currentMaxNum;
    let csi = SBSconfig.currentStepIndex;
```

Эти строки выполнялись **один раз** при вызове `SBSoutput()` из `main.js:18`, то есть при загрузке страницы, когда `SBSconfig.currentStepIndex` ещё `0`. Дальше `csi` жил своей жизнью и в `SBSconfig` не возвращался. То же с `visibleMax` — цикл на строках 58-62 обновлял локальную переменную, а `SBSconfig.currentMaxNum` навсегда оставался `0n`.

Следствие: внешний мир не знал реального прогресса. Возобновить с нужного места было невозможно — снаружи видно `currentStepIndex === 0`.

### Баг 3 — индексы батча смещены на длину батча

```js
csi = csi + currentBatch.length;      // строка 65 — сначала сдвинули

SBSconfig.batchStartIndex = csi;      // строка 67 — потом записали как "начало"
SBSconfig.batchEndIndex = csi + currentBatch.length - 1;
```

`csi` увеличивается **до** записи индексов. В результате `batchStartIndex` указывает на начало *следующего* батча, а `batchEndIndex` улетает ещё дальше. При `batchSize = 10` и первом батче: реальные индексы `0..9`, а записано `10..19`.

### Баг 4 — событие уходило в никуда

```js
const SBSeventTarget = new EventTarget();   // строка 7
...
sendSBS_Data(SBSconfig, currentBatch, SBSeventTarget, ...);   // строка 70
```

`SBSeventTarget` — локальная константа модуля, наружу не экспортировалась. Подписаться на неё было неоткуда. Каждый батч аккуратно упаковывался в `CustomEvent` и отправлялся в объект, который никто не слушает.

При этом `sequenceView.js` слушал `stateTarget` — **другой** объект, и вдобавок событие `collatz_done`, а не `sbs_batch`. Обработчик был пустой.

### Баг 5 — событие не несло данных

```js
const SBSData_BatchEvent = new CustomEvent('sbs_batch', {
    detail: { status: 'batch' }        // и всё
});
```

Даже если бы подписчик существовал, он получил бы строку `'batch'` и ничего больше.

**Итог до патча:** числа считались, но на экран не попадали никогда. Кнопка меняла иконку, но ни на что не влияла.

## 1. `events.js` — событие как самодостаточное сообщение

```diff
     const SBSData_BatchEvent = new CustomEvent('sbs_batch', {
         detail: {
-            status: 'batch'
+            status: 'batch',
+            batch: data,
+            startIndex,
+            endIndex
         }
     });
```

**Идея:** событие должно быть самодостаточным. Подписчик получает всё нужное прямо в `detail` и не обязан лезть в глобальный `SBSconfig`.

Почему это принципиально, а не косметика: если подписчик читает `SBSconfig.currentBatch` в момент обработки, он читает **актуальное на сейчас** значение. При быстрой скорости (`intervalMs = 0`) состояние может уже уехать вперёд. Данные в `detail` — это снимок, он не протухает. Событие описывает то, что произошло, а не отсылает к изменяемому состоянию.

Обратите внимание: `sendSBS_Data` по-прежнему **и** пишет в `item` (строки 35-37), **и** кладёт в `detail`. То есть состояние обновляется для тех, кому нужен «текущий срез», а событие несёт копию для подписчиков. Двойная бухгалтерия, но осознанная.

Плюс новая функция:

```js
export function sendSBS_Done(target) {
    const SBSDoneEvent = new CustomEvent('sbs_done', {
        detail: { status: 'done' }
    });
    target.dispatchEvent(SBSDoneEvent);
}
```

**Зачем отдельное событие завершения.** Кнопка Play/Pause должна вернуться в состояние «Запустить», когда последовательность досчиталась сама. Без события UI пришлось бы опрашивать `SBSconfig.doneRunning` по таймеру. Событие — это push вместо polling.

> **Расхождение с вашим текущим кодом.** В репозитории уже есть `sendSBS_DoneEvent` (не `sendSBS_Done`) и дополнительно `sendSBS_ClearEvent`. Патч писался под более раннюю версию. При применении имя надо согласовать — иначе импорт в `SBSoutputManager.js` упадёт.

## 2. `SBSoutputManager.js` — ядро патча

Это 80% изменений. Разберём по концепциям.

### 2.1. Состояние переехало из замыкания в `SBSconfig`

Было:

```js
export function SBSoutput() {
    let visibleMax = SBSconfig.currentMaxNum;   // копия, снятая один раз
    let csi = SBSconfig.currentStepIndex;       // копия, снятая один раз

    const startSBS = () => { /* работает с csi и visibleMax */ }
```

Стало:

```js
function runSBSTick() {
    const startIndex = SBSconfig.currentStepIndex;   // читаем каждый тик
    ...
    SBSconfig.currentStepIndex = startIndex + currentBatch.length;   // пишем обратно
```

**Концепция: single source of truth.** Прогресс существует ровно в одном месте — `SBSconfig`. Любой модуль в любой момент видит настоящее положение дел.

Именно это делает паузу и возобновление возможными в принципе. `resumeSBS()` просто читает `SBSconfig.currentStepIndex` и продолжает оттуда. Никакого «а где мы там остановились» — состояние снаружи, оно переживает остановку функции.

То же с максимумом:

```js
for (let i = 0; i < currentBatch.length; i++) {
    if (SBSconfig.currentMaxNum === 0n || currentBatch[i] > SBSconfig.currentMaxNum) {
        SBSconfig.currentMaxNum = currentBatch[i];
    }
}
```

Сравнение и запись идут прямо в `SBSconfig`. Ваш комментарий на строках 52-55 старого файла («I need to check all numbers in the batch») ИИ учёл — проверяются все элементы батча, а не только последний. И `Math.max` не используется, потому что он не работает с BigInt — это вы тоже отметили в строке 57, и ИИ сохранил ручной цикл.

### 2.2. Таймер стал управляемым ресурсом

```js
let timerId = null;

function clearSBSTimer() {
    if (timerId !== null) {
        clearTimeout(timerId);
        timerId = null;
    }
}
```

**Концепция: владение ресурсом.** Всё, что запускается асинхронно, должно иметь идентификатор, и этот идентификатор нужно хранить. Иначе ресурс неуправляем.

Обнуление `timerId = null` после `clearTimeout` — не паранойя. Оно отличает «таймер висит» от «таймера нет», что даёт `clearSBSTimer()` идемпотентность: вызвать дважды безопасно. Также внутри самого коллбэка:

```js
timerId = setTimeout(() => {
    timerId = null;        // тик начался, старый id больше не актуален
    runSBSTick();
}, intervalMs);
```

Без этой строки после срабатывания таймера в `timerId` остался бы «мёртвый» идентификатор, и последующий `clearTimeout` работал бы вхолостую, создавая ложное ощущение контроля.

`clearSBSTimer()` вызывается **первым делом** в `startSBS`, `pauseSBS`, `resumeSBS`, `finishSBS`. Это защита от гонки: если пользователь быстро жмёт паузу и старт, старая цепочка тиков гарантированно убита до запуска новой. Иначе два цикла работали бы параллельно, оба писали бы в `SBSconfig.currentStepIndex`, и вывод шёл бы с дырами и дублями.

### 2.3. Явные операции вместо одной перегруженной

Вместо одной `startSBS` внутри замыкания появились четыре функции с разными обязанностями:

```js
export function startSBS()    // новый прогон с нуля
export function pauseSBS()    // остановить, позицию сохранить
export function resumeSBS()   // продолжить с сохранённой позиции
function finishSBS()          // естественное завершение (не экспортируется)
```

**Концепция: named operations вместо флаг-жонглирования.** Раньше `PlayOrPause` инвертировал булеву переменную и надеялся, что цикл сам разберётся. Теперь каждое намерение — отдельный вызов с чётким контрактом.

Ключевая разница между `startSBS` и `resumeSBS`:

```js
export function startSBS() {
    clearSBSTimer();
    SBSconfig.currentStepIndex = 0;      // сброс всего
    SBSconfig.visibleItems = [];
    SBSconfig.currentMaxNum = 0n;
    ...
    runSBSTick();
}

export function resumeSBS() {
    if (SBSconfig.doneRunning) return;              // защита
    if (state.workerResult.length === 0) return;    // защита
    clearSBSTimer();
    SBSconfig.isRunning = true;                     // НЕ трогаем currentStepIndex
    runSBSTick();
}
```

`startSBS` обнуляет прогресс, `resumeSBS` его сохраняет. Это разные операции, и путать их нельзя — раньше они были одной функцией.

Обратите внимание на `resumeSBS`. Раньше это была переменная:

```js
export let resumeSBS = null;    // старый код, строка 10
...
resumeSBS = startSBS;           // строка 80, присваивается внутри SBSoutput()
```

То есть до вызова `SBSoutput()` импортировавшие её модули видели `null`. Хуже: `export let` с поздним присваиванием — это живая привязка, работающая только при удачном порядке инициализации. `playButtonSVG.js:3` импортировал `resumeSBS` и мог получить `null`. Патч делает её обычной функцией — она существует с момента загрузки модуля.

### 2.4. Два условия завершения вместо одного

```js
if (startIndex >= workerResultLen) {     // проверка ДО работы
    finishSBS();
    return;
}
...
if (currentBatch.length === 0) {         // подстраховка после slice
    finishSBS();
    return;
}
...
if (SBSconfig.currentStepIndex >= workerResultLen) {   // проверка ПОСЛЕ работы
    finishSBS();
    return;
}
```

**Зачем третья проверка (после отправки батча).** Без неё последний батч отправлялся бы, затем планировался лишний `setTimeout`, и только следующий тик обнаружил бы конец. Это лишняя задержка `intervalMs` перед возвратом кнопки в исходное состояние. Проверка «после» завершает цикл сразу, как только данные исчерпаны.

Старый код на строках 43-47 вместо этого ловил `undefined` и писал `console.error('Index overflow')` — то есть нормальное окончание последовательности трактовалось как ошибка.

Также источник длины сменился:

```diff
-        const workerResultLen = state.workerListLen;
+    const workerResultLen = state.workerResult.length;
```

`state.workerListLen` заполняется из `e.data.steps` (`workerManager.js:28`) — это **количество шагов**, а не длина массива. Числа могут отличаться (последовательность из N шагов содержит N+1 элемент). Патч берёт длину напрямую у массива — единственный надёжный источник.

### 2.5. Санитизация входных значений

```js
const batchSize = Math.max(1, Number(speedState.batchSize) || 1);
const intervalMs = Math.max(0, Number(speedState.intervalMs) || 0);
```

**Зачем.** `speedState` заполняется из веб-компонента `speedController.js`, а значения DOM-инпутов — строки. `"10"` вместо `10`. При `slice(0, 0 + "10")` JS сделает неявное приведение и, скорее всего, сработает, но при `startIndex + batchSize` получится конкатенация: `0 + "10" = "010"`. Тихая катастрофа.

`Number(...)` приводит явно. `|| 1` ловит `NaN` (если инпут пустой) и `0` (недопустимый размер батча). `Math.max(1, ...)` гарантирует, что батч не будет нулевым — иначе `slice` вернёт пустой массив, и цикл встанет намертво, никогда не двигая `currentStepIndex`.

Это защитное программирование на границе: данные приходят из внешнего мира (DOM), их нельзя доверять.

### 2.6. `SBSoutput()` сжалась до подписки

```js
export function SBSoutput() {
    stateTarget.addEventListener('collatz_done', () => {
        startSBS();
    });
}
```

Раньше эта функция была контейнером для всего: состояния, цикла, подписки. Теперь у неё одна работа — связать «воркер досчитал» с «начать вывод». Это точка инициализации, вызывается один раз из `main.js:18`.

Вся логика вынесена на уровень модуля, где она доступна другим файлам через `export`.

### 2.7. Целевой EventTarget сменился

```diff
-        sendSBS_Data(SBSconfig, currentBatch, SBSeventTarget, ...);
+    sendSBS_Data(SBSconfig, currentBatch, stateTarget, startIndex, endIndex);
```

Локальный `SBSeventTarget` удалён, всё идёт через общий `stateTarget`. Это чинит Баг 4: теперь события попадают туда, где их слушают.

**Архитектурный смысл:** одна общая шина событий на приложение. Модулям не надо знать, какой именно объект-передатчик импортировать под какое событие — достаточно `stateTarget` и имени события.

Компромисс: при росте проекта общая шина превращается в свалку. Но на текущем размере (десяток модулей) это упрощение оправдано — альтернатива требовала бы экспортировать и импортировать несколько таргетов.

И индексы теперь передаются корректные — `startIndex` снят **до** сдвига счётчика, `endIndex` вычислен от него же (чинит Баг 3).

## 3. `playButtonSVG.js` — разделение представления и логики

Было — кнопка сама решала, что происходит:

```js
export function PlayOrPause() {
    SBSconfig.isRunning = !SBSconfig.isRunning;   // меняет состояние
    ...
    pauseSBS();                                    // вызывает логику
```

Стало — кнопка только рисует:

```js
export function setRunButtonMode(isPlaying) {
    if (!runButton) return;
    if (isPlaying) { /* иконка паузы */ }
    else { /* иконка play */ }
}
```

**Концепция: «тупое» представление (dumb view).** Функция принимает булев параметр и рисует. Она не читает глобальное состояние, не меняет его, не вызывает бизнес-логику. Чистая функция отображения.

Что это даёт:

1. **Убрана циклическая зависимость.** Было: `playButtonSVG` → `SBSoutputManager` → (через `resumeSBS`) обратно. Стало: `playButtonSVG` ни от чего логического не зависит. Импорты `SBSconfig` и `pauseSBS` удалены.
2. **Убрано «двойное владение» флагом.** Раньше `isRunning` меняли и кнопка, и цикл вывода. Два владельца одной переменной — классический источник рассинхрона: кнопка думает «играем», цикл думает «стоим».
3. **Кнопку можно синхронизировать извне.** Когда последовательность завершилась сама, `runProcessControls` ловит `sbs_done` и зовёт `setRunButtonMode(false)`. С прежней инвертирующей функцией это было бы невозможно — она бы просто перевернула флаг, не зная реального положения.

Разница между «переключи» и «установи» здесь фундаментальна. Toggle зависит от предыдущего состояния и может рассинхронизироваться. Setter — идемпотентен: вызови `setRunButtonMode(false)` десять раз, результат одинаковый.

Старое имя оставлено ради совместимости:

```js
export function PlayOrPause() {
    setRunButtonMode(false);
}
```

Заглушка, чтобы не сломать импорты, которые ИИ мог не увидеть. По-хорошему её надо удалить после проверки.

Побочно исправлена кодировка русских строк: `"РџР°СѓР·Р°"` → `"Пауза"` (mojibake от неверной интерпретации UTF-8).

## 4. `runProcessControls.js` — единый центр принятия решений

Ключевой архитектурный ход патча. Вся логика «что делать по клику» собрана в одном обработчике:

```js
runProcess_Elements.runButton.addEventListener('click', () => {
    // Ветка 1: идёт вывод → пауза
    if (SBSconfig.isRunning) {
        pauseSBS();
        setRunButtonMode(false);
        return;
    }

    // Ветка 2: есть незаконченный прогон → продолжить
    const hasResult = state.workerResult.length > 0;
    const canResume = hasResult &&
        !SBSconfig.doneRunning &&
        SBSconfig.currentStepIndex < state.workerResult.length;

    if (canResume) {
        resumeSBS();
        setRunButtonMode(true);
        return;
    }

    // Ветка 3: новый расчёт (валидация → сброс → воркер)
    ...
});
```

**Концепция: state machine на одной кнопке.** Одна физическая кнопка обслуживает три разных сценария. Решение принимается по текущему состоянию, а не по внутреннему флагу самой кнопки.

Разберём условие `canResume` — оно точнее, чем кажется:

- `hasResult` — есть ли вообще что выводить. Без данных возобновлять нечего.
- `!SBSconfig.doneRunning` — последовательность не досмотрена до конца. Если досмотрена, клик должен запустить **новый** расчёт, а не пытаться продолжить с конца.
- `currentStepIndex < length` — остались невыведенные элементы. Страховка на случай, если `doneRunning` по какой-то причине не выставился.

Последние два условия частично дублируют друг друга — это намеренная избыточность. Если один флаг рассинхронизируется, второй ловит ошибку.

**Ранние возвраты (`return` в каждой ветке)** — приём против «провала» в следующую ветку. Без них после `pauseSBS()` управление пошло бы дальше, дошло до валидации инпута и запустило новый расчёт. Каждая ветка обязана завершать обработчик.

### `resetRunData()` — гигиена перед новым прогоном

```js
function resetRunData() {
    state.workerResult = [];
    state.workerListLen = 0;
    state.workerMaxNum = 0n;
    state.errorCause = null;

    SBSconfig.currentStepIndex = 0;
    SBSconfig.isRunning = false;
    ...
}
```

Вызывается **перед** отправкой значения в воркер. Критично, потому что `sendCollatz_MainData` (`events.js:4`) делает `push` в существующий массив:

```js
item[st].push(...data.data);
```

Без сброса второй расчёт **дописался бы** к первому. Вы бы увидели последовательность для числа 27, а следом — для числа 5, как одну.

Ровно про эту функцию мы говорили в прошлом сообщении: ручное перечисление полей — уязвимое место. Фабрика `createSBSconfig()` решает это надёжнее.

### Подписка на завершение

```js
stateTarget.addEventListener('sbs_done', () => {
    setRunButtonMode(false);
});
```

Регистрируется **до** обработчика клика, при вызове `RunSequenceCalc()`. Когда вывод досчитался сам, кнопка возвращается в «Запустить» без участия пользователя. Замыкает контур обратной связи: логика уведомляет UI, а не UI опрашивает логику.

## 5. `sequenceView.js` — подключение отрисовки

Было (пустая заглушка на неправильном событии):

```js
stateTarget.addEventListener('collatz_done', () => {
    
});
```

Стало:

```js
stateTarget.addEventListener('sbs_batch', (event) => {
    const { batch, startIndex } = event.detail;

    for (let i = 0; i < batch.length; i++) {
        txtListObj_create(seqList_Elements.txtList, startIndex + i + 1, batch[i]);
    }
});
```

**Смена события — смысловой сдвиг.** `collatz_done` означает «воркер посчитал всё» — если рисовать по нему, весь список вывалится мгновенно, и вся идея пошагового вывода теряется. `sbs_batch` означает «готова очередная порция» — рисуем по мере поступления. Именно это и есть Step-By-Step.

**Арифметика индекса.** `startIndex` — позиция в массиве (с нуля), `+ i` — смещение внутри батча, `+ 1` — перевод в человеческую нумерацию (список начинается с 1, а не с 0). Здесь `startIndex` — это уже исправленное значение из п. 2.4, снятое до сдвига счётчика.

`txtListObj_create` (`sequenceView_Logic.js:3`) сам определяет чётность через `(number & 1n) === 0n` и вешает тег `÷ 2` или `× 3 + 1`. Побитовое `&` с BigInt-литералом `1n` — корректный способ проверки чётности для BigInt, обычный `% 2` тоже работал бы, но медленнее.

## 6. `main.js` — импорт ради side-effect

```diff
 import '../webComponents/speedController.js';
+import './visualisation/viewModes/sequenceView.js';
```

**Концепция: side-effect import.** Импорт без фигурных скобок и без имени. Ничего не извлекается — важен сам факт выполнения модуля.

`sequenceView.js` не экспортирует функций. Его подписка `addEventListener` находится на верхнем уровне и срабатывает при загрузке модуля. Если модуль никто не импортирует, браузер его просто не загрузит, и подписки не будет.

Именно поэтому раньше отрисовка не работала бы, даже если бы обработчик был непустым — файл не был подключён вообще.

Рядом в том же стиле уже импортируется `speedController.js` — там регистрируется веб-компонент, тоже чистый side-effect. Приём одинаковый.

## 7. Итоговая архитектура

Поток данных после патча:

```
[клик по кнопке]
      │
      ├─ isRunning? ──────► pauseSBS() + setRunButtonMode(false)
      │
      ├─ canResume? ──────► resumeSBS() + setRunButtonMode(true)
      │
      └─ иначе ─► валидация ─► resetRunData() ─► workerManager_Recieve()
                                                        │
                                                  [Web Worker считает]
                                                        │
                                          state.workerResult наполняется
                                                        │
                                          событие 'collatz_done' → stateTarget
                                                        │
                                                   startSBS()
                                                        │
                                    ┌──────────► runSBSTick() ◄─────────┐
                                    │                 │                 │
                                    │      батч в SBSconfig.visibleItems│
                                    │      обновление currentMaxNum     │
                                    │      сдвиг currentStepIndex       │
                                    │                 │                 │
                                    │      событие 'sbs_batch' ─────────┼──► sequenceView
                                    │                 │                 │    рисует DOM
                                    │        данные кончились?          │
                                    │           нет ──► setTimeout ─────┘
                                    │           да  ──► finishSBS()
                                    │                       │
                                    │            событие 'sbs_done' ──► кнопка в "Запустить"
```

### Принципы, которые ИИ применил

| Принцип | Где именно | Что даёт |
|---|---|---|
| Single source of truth | Состояние только в `SBSconfig`, не в замыкании | Пауза/возобновление становятся возможны |
| Владение ресурсом | `timerId` хранится и очищается | Цикл можно остановить |
| Разделение представления и логики | `setRunButtonMode` только рисует | Нет циклических зависимостей, нет двойного владения флагом |
| Named operations вместо флагов | `start`/`pause`/`resume`/`finish` | Явные намерения вместо угадывания по булеву |
| Самодостаточные события | Данные в `detail`, не ссылка на состояние | Подписчик не читает протухшее состояние |
| Идемпотентность | `setRunButtonMode(false)`, `clearSBSTimer()` | Безопасно вызывать повторно |
| Санитизация на границе | `Number(...) || fallback` | Строки из DOM не ломают арифметику |
| Ранние возвраты | Ветки обработчика клика | Нет провала в соседний сценарий |

## 8. Что стоит перепроверить перед применением

Патч писался под более раннюю версию репозитория. Расхождения с текущим кодом:

1. **Имя функции.** В патче `sendSBS_Done`, у вас уже есть `sendSBS_DoneEvent`. Импорт в `SBSoutputManager.js` упадёт, если не согласовать.
2. **Потерянный функционал.** В вашей версии есть `SBSoutput_clear()` и `sendSBS_ClearEvent` — патч про них не знает и при слепом применении затрёт.
3. **`resetSBS`.** Текущий `SBSoutputManager.js:3` импортирует `resetSBS` из `stateManager.js`, но эта функция пустая (`stateManager.js:29-31`). Патч вместо неё вводит `resetRunData()` в `runProcessControls.js` — то есть логика сброса оказывается в UI-слое, хотя логичнее ей жить в `stateManager`.
4. **Дубли сброса.** После патча обнуление `SBSconfig` встречается в двух местах: `startSBS()` и `resetRunData()`. Это тот самый рассинхрон, о котором шла речь — добавите поле, забудете в одном из мест.
5. **Заглушка `PlayOrPause`.** Оставлена для совместимости. Проверьте, кто её ещё импортирует, и удалите.
6. **`export let currentBatch`** на уровне модуля сохранён, хотя данные теперь идут через событие. Дублирующий канал, кандидат на удаление.

**Рекомендация:** применять не целиком, а по частям, начиная с `SBSoutputManager.js` — там основная ценность. Сброс состояния лучше сразу свести к одной фабрике в `state.js`, а не тиражировать ручные присваивания.
