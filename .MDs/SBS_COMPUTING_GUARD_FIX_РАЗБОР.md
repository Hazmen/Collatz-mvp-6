# SBS_COMPUTING_GUARD_FIX — подробный разбор патча

Файл объясняет, что сделал ИИ в патче `SBS_COMPUTING_GUARD_FIX.patch`, зачем и какая идея за этим стоит.

Патч крошечный — 6 добавленных строк в трёх файлах. Но он закрывает целый класс багов, поэтому разберём подробно.

| Файл | Изменение |
|---|---|
| `state/state.js` | Новое поле `isComputing: false` |
| `workers/workerManager.js` | Выставление флага в 3 точках жизненного цикла воркера |
| `ui/runProcessControls.js` | Сброс флага при ресете + guard в обработчике клика |

> **Важно:** этот патч — надстройка над `SBS_PAUSE_RESUME_FIX`. Он опирается на `resetRunData()` и на структуру обработчика клика с ветками, которые появляются только там. Применять его в одиночку нельзя.

---

## 0. Проблема, которую он решает

### Асинхронный разрыв

Посмотрите на текущий `runProcessControls.js:20`:

```js
workerManager_Recieve(getSpecificState('activeInputValue'));
```

и на саму функцию (`workerManager.js:11-13`):

```js
export function workerManager_Recieve(inputValue) {
    worker.postMessage(inputValue);
};
```

`postMessage` возвращает управление **мгновенно**. Он не ждёт ответа — он кладёт сообщение в очередь воркера и завершается. Расчёт идёт в другом потоке.

Между «отправили задачу» и «получили `collatz_done`» проходит время. Для числа 27 — миллисекунды. Для числа с сотнями знаков — секунды или десятки секунд. Всё это время интерфейс полностью отзывчив: кнопка нажимается, обработчики срабатывают.

**И в этом окне состояние приложения не описано никаким флагом.**

Проверим по `SBSconfig` в этот момент:

- `isRunning` — `false` (вывод ещё не начался, `startSBS` вызывается только по `collatz_done`)
- `doneRunning` — `false` (ничего не завершалось)
- `currentStepIndex` — `0`
- `state.workerResult` — пустой массив (или частично наполненный чанками)

Теперь примерим это к логике клика из предыдущего патча:

```js
if (SBSconfig.isRunning) { ... }        // false → не сработает

const hasResult = state.workerResult.length > 0;   // false → не сработает
const canResume = hasResult && ...;

// проваливаемся в ветку 3 — новый расчёт
```

Второй клик во время вычисления неотличим от первого клика на чистом приложении. Приложение запустит **второй** расчёт поверх первого.

### Что ломается конкретно

**Смешение результатов.** `sendCollatz_MainData` (`events.js:4`) дописывает чанки:

```js
item[st].push(...data.data);
```

Воркер один (`workerManager.js:5` — создаётся единожды на уровне модуля). Он обработает сообщения последовательно: сначала задачу А, потом задачу Б. Но `resetRunData()` вызывается в момент **отправки** Б, а не в момент начала её обработки.

Хронология при двух кликах:

```
t0  клик 1 → resetRunData() → postMessage(27)
t1  воркер начал считать 27, шлёт чанки → workerResult = [27, 82, 41, ...]
t2  клик 2 → resetRunData() → workerResult = []  ← ЧАНКИ ЗАДАЧИ 27 СТЁРТЫ
              postMessage(5)
t3  воркер ДОсчитывает 27, шлёт остаток чанков → workerResult = [хвост от 27]
t4  воркер шлёт 'done' по задаче 27
      → collatz_done → startSBS() запускает вывод обрывка
t5  воркер начал считать 5, шлёт чанки → workerResult = [хвост 27, 5, 16, 8...]
t6  воркер шлёт 'done' по задаче 5
      → collatz_done → startSBS() ВТОРОЙ РАЗ
```

На выходе — массив-франкенштейн и два конкурирующих запуска вывода.

**Двойной запуск вывода.** В `SBSoutput()` подписка на `collatz_done` регистрируется один раз, но событие приходит дважды. Каждое вызывает `startSBS()`. Второй `startSBS` обнуляет `currentStepIndex` и `visibleItems` посреди работы первого. При этом DOM уже содержит нарисованные элементы от первого прогона — `sequenceView.js` их не удаляет, он только `appendChild`. Список получает дубли.

Спасает ли `clearSBSTimer()` внутри `startSBS`? Частично — он убьёт таймер первого цикла. Но нарисованное в DOM останется, а нумерация пойдёт заново с 1. Визуально — каша.

**Рассинхрон кнопки.** `setRunButtonMode(true)` вызывается на каждом клике. Иконка показывает «Пауза», хотя пауза в этот момент бессмысленна — паузить нечего, вывод не идёт. Нажатие на «Паузу» уйдёт в ветку `if (SBSconfig.isRunning)`, которая `false`, и снова запустит расчёт. Каскад.

## 1. `state.js` — новое поле

```diff
 export const state = {
     activeInputValue: 0n,
     inputError: false,
+    isComputing: false,
     workerResult: [],
```

**Концепция: явное представление промежуточного состояния.**

До патча жизненный цикл приложения описывался неполно. Были состояния «покой», «идёт вывод», «вывод завершён» — но не было «идёт вычисление». Это состояние существовало физически (воркер работал), но не было отражено в модели данных. Код не мог о нём спросить.

Обратите внимание на закомментированную строку в самом верху вашего `state.js:2`:

```js
// status: 'idle', // idle - untouched; computing - in process of adding new data; error - error; ready
```

Вы сами это спроектировали — там даже есть значение `computing`. ИИ, по сути, реализовал ваш замысел, но в виде булева флага, а не строкового enum.

### Булев флаг против строкового статуса

Ваш исходный вариант (`status: 'idle' | 'computing' | 'error' | 'ready'`) строже: состояния взаимоисключающие по построению. Нельзя быть одновременно `computing` и `ready` — поле одно.

Вариант ИИ (отдельный `isComputing` рядом с `SBSconfig.isRunning`, `SBSconfig.doneRunning`) допускает бессмысленные комбинации. Например, `isComputing === true` и `isRunning === true` одновременно — состояние, которого быть не должно, но которое типы не запрещают.

Почему ИИ выбрал флаг: минимальная инвазивность. Строковый статус потребовал бы переписать все проверки во всех модулях. Флаг добавляется точечно и ничего не ломает.

Для текущего размера проекта это разумный компромисс. Но когда состояний станет 5-6, стоит вернуться к вашей исходной идее с `status` — иначе флаги начнут противоречить друг другу.

## 2. `workerManager.js` — флаг покрывает весь жизненный цикл

Три точки. Одна поднимает флаг, две опускают.

### Подъём — при отправке

```diff
 export function workerManager_Recieve(inputValue) {
+    state.isComputing = true;
     worker.postMessage(inputValue);
 };
```

**Строка стоит ДО `postMessage`, и это принципиально.**

JavaScript однопоточен: между этими двумя строками никакой чужой код выполниться не может, так что технически порядок здесь не критичен. Но порядок «сначала объявили намерение, потом совершили действие» — правильная привычка. Если завтра `postMessage` обернут в `try/catch` или добавят предварительную проверку с ранним выходом, флаг уже будет выставлен корректно.

Флаг живёт в `state`, а не в модуле `workerManager`. Это осознанно: `runProcessControls` должен его читать, а импортировать внутренности воркер-менеджера ради одного флага — лишняя связанность. Общее состояние для того и существует.

### Спуск — при успехе

```diff
     if (e.data.type === 'done') {
+        state.isComputing = false;
 
         setToogleSwitch('collatz_received', true);
         ev.sendCollatz_SecondaryData( state, e.data.max, e.data.steps, stateTarget );
     }
```

**Порядок здесь уже критичен по-настоящему.**

`sendCollatz_SecondaryData` диспатчит `collatz_done` (`events.js:17`). `dispatchEvent` вызывает всех подписчиков **синхронно**, прямо внутри вызова. Один из подписчиков — `startSBS()` в `SBSoutputManager`.

Значит, к моменту возврата из `sendCollatz_SecondaryData` вывод уже успел стартовать и, возможно, отрисовать первый батч. Если бы `isComputing = false` стояло **после** этой строки, то во время работы `startSBS` флаг всё ещё был бы `true`. Любая проверка `if (state.isComputing) return;` внутри цепочки заблокировала бы легитимную работу.

Правило: **сбрасывать флаг до диспатча события, а не после.** Состояние должно быть консистентным на момент уведомления подписчиков.

Тот же принцип, что и в `finishSBS()` из предыдущего патча:

```js
function finishSBS() {
    clearSBSTimer();
    SBSconfig.isRunning = false;
    SBSconfig.doneRunning = true;
    sendSBS_Done(stateTarget);      // событие идёт ПОСЛЕ обновления флагов
}
```

Подписчик `sbs_done` увидит уже финальное состояние, а не промежуточное.

### Спуск — при ошибке

```diff
     if (e.data.type === 'error') {
+        state.isComputing = false;
         ev.sendCollatz_ErrorData( state, 'Something went wrong :(', stateTarget );
     }
```

**Самая важная из трёх строк.**

Без неё после первой же ошибки в воркере флаг застревает в `true` навсегда. Guard в UI начинает блокировать **все** последующие клики. Приложение выглядит полностью зависшим, хотя ничего не считает.

Это классическая ловушка любого флага «занято»: путь успеха разработчик снимает почти всегда, путь ошибки забывает регулярно.

**Концепция: каждый путь выхода должен снимать флаг.** Не «основной путь», а каждый. Если бы код был на промисах, здесь был бы `finally` — конструкция, которая существует ровно для этой задачи.

### Дыры, которые патч не закрыл

Честная оценка: покрытие неполное.

**Нет `worker.onerror`.** `e.data.type === 'error'` ловит только те ошибки, которые воркер сам поймал и отправил сообщением. Если внутри воркера случится необработанное исключение или синтаксическая ошибка, сработает `worker.onerror` — а такого обработчика в `workerManager.js` нет вообще. Флаг зависнет.

Добавить стоило бы:

```js
worker.onerror = (e) => {
    state.isComputing = false;
    ev.sendCollatz_ErrorData(state, e.message, stateTarget);
};
```

**Нет таймаута.** Если воркер уйдёт в бесконечный цикл (гипотеза Коллатца не доказана — теоретически возможна последовательность без завершения), ни `done`, ни `error` не придут никогда. Флаг зависнет, интерфейс заблокируется навсегда.

**Нет отмены.** Заметьте комментарий в вашем `stateManager.js:4`:

```js
// terminateWorker();  // TODO: убить текущий воркер
```

Вы это предусмотрели. Патч эту задачу не решает — он предотвращает второй запуск, но не даёт прервать текущий. Правильное решение было бы `worker.terminate()` + пересоздание воркера, тогда кнопка во время вычисления могла бы работать как «Отмена», а не как заглушка.

## 3. `runProcessControls.js` — сброс и guard

### Сброс в `resetRunData()`

```diff
     state.errorCause = null;
+    state.isComputing = false;
```

Новое поле добавлено в функцию полного сброса — логично и последовательно.

Но именно здесь видна проблема, о которой шла речь раньше: **список полей приходится синхронизировать вручную в нескольких местах**. Добавили поле в `state` — не забудьте про `resetRunData`. Забыли — получите утечку состояния между сессиями.

Это ровно тот аргумент в пользу фабрики `createSBSconfig()` / `createState()`. С фабрикой строка `state.isComputing = false` в патче была бы не нужна вообще — поле сбрасывалось бы автоматически, потому что оно есть в фабрике.

Патч из 6 строк, одна из которых существует только из-за отсутствия фабрики. Показательно.

### Guard в обработчике

```diff
     runProcess_Elements.runButton.addEventListener('click', () => {
+        if (state.isComputing) return;
+
         if (SBSconfig.isRunning) {
             pauseSBS();
```

**Одна строка, но её позиция определяет всё.**

Она стоит **первой** — до всех остальных веток. Это делает её абсолютным приоритетом: пока идёт вычисление, обработчик не выполняет вообще ничего. Не паузит, не возобновляет, не валидирует ввод, не сбрасывает данные.

Почему именно первой, а не, скажем, перед третьей веткой (запуском нового расчёта). Логика: во время вычисления **все** остальные действия бессмысленны или вредны.

- Пауза — паузить нечего, вывод не идёт.
- Возобновление — `workerResult` пуст или наполняется прямо сейчас, продолжать не с чего.
- Новый расчёт — то самое смешение результатов.

Guard на самом верху отсекает весь класс проблем разом, а не латает отдельные ветки.

**Концепция: guard clause.** Это устоявшийся приём — проверка предусловия с немедленным выходом в начале функции. Альтернатива (обернуть всё тело в `if (!state.isComputing) { ... }`) добавила бы уровень вложенности всему обработчику и хуже читалась бы.

### Молчаливый возврат — компромисс

`return` без объяснения. Пользователь жмёт кнопку — не происходит ничего. Ни сообщения, ни визуальной реакции. Для длинных вычислений это выглядит как зависший интерфейс.

Правильнее было бы отражать состояние в UI: третий режим кнопки со спиннером, `disabled`, текст «Вычисляю…». Тогда guard стал бы страховкой на случай программного вызова, а не единственной линией обороны.

Заготовка для этого есть — `setRunButtonMode` из предыдущего патча принимает булев параметр. Расширить до трёх состояний несложно:

```js
export function setRunButtonMode(mode) {   // 'idle' | 'playing' | 'computing'
```

Патч этого не делает, потому что решает узкую задачу — предотвратить порчу данных. Это разумный скоуп для отдельного патча.

## 4. Полная модель состояний после обоих патчей

```
                    ┌──────────────────┐
                    │      ПОКОЙ       │  isComputing=false
                    │  (idle)          │  isRunning=false
                    └────────┬─────────┘  doneRunning=false
                             │ клик → валидация → resetRunData()
                             │        → workerManager_Recieve()
                             ▼
                    ┌──────────────────┐
                    │   ВЫЧИСЛЕНИЕ     │  isComputing=TRUE
                    │  (computing)     │  ← КЛИКИ ЗАБЛОКИРОВАНЫ guard'ом
                    └────┬────────┬────┘
                'error'  │        │  'done'
                         │        │  (isComputing=false ПЕРЕД событием)
                         ▼        ▼
              ┌──────────┐   ┌──────────────────┐
              │  ОШИБКА  │   │      ВЫВОД       │  isRunning=true
              └──────────┘   │   (running)      │
                             └────┬────────┬────┘
                          клик    │        │  данные кончились
                        pauseSBS()│        │  finishSBS()
                                  ▼        ▼
                       ┌──────────────┐  ┌──────────────┐
                       │    ПАУЗА     │  │  ЗАВЕРШЕНО   │ doneRunning=true
                       │  isRunning=  │  │  событие     │
                       │     false    │  │  'sbs_done'  │
                       └──────┬───────┘  └──────┬───────┘
                              │ клик             │ клик
                              │ resumeSBS()      │ → новый расчёт
                              ▼                  │   (canResume=false из-за
                          [ВЫВОД]                │    doneRunning)
                                                 ▼
                                             [ПОКОЙ]
```

Патч `COMPUTING_GUARD` добавил в эту схему ровно один узел — «ВЫЧИСЛЕНИЕ» — и запретил из него любые переходы, кроме тех, что инициирует сам воркер.

Как `isComputing` взаимодействует с `canResume`. Во время вычисления `workerResult` может быть частично наполнен (чанки приходят порциями), то есть `hasResult` станет `true`, и `canResume` тоже. Без guard'а клик привёл бы к `resumeSBS()` на неполных данных — вывод показал бы обрывок и завершился раньше времени. Guard стоит выше и до этой проверки не доходит.

## 5. Идеи патча в сжатом виде

| Идея | Реализация | Что предотвращает |
|---|---|---|
| Асинхронное состояние должно быть представлено явно | Поле `isComputing` | «Слепое пятно» между отправкой и ответом |
| Флаг снимается на **каждом** пути выхода | 2 точки сброса: `done` и `error` | Вечная блокировка после ошибки |
| Состояние обновляется **до** диспатча события | `isComputing = false` перед `sendCollatz_SecondaryData` | Подписчик видит консистентное состояние |
| Guard clause на входе | `if (state.isComputing) return;` первой строкой | Весь класс проблем повторного клика разом |
| Новое поле — в функцию сброса | Строка в `resetRunData()` | Утечка состояния между сессиями |

### Более общий принцип

Патч иллюстрирует правило: **любая асинхронная операция должна иметь наблюдаемое состояние «в процессе»**.

Это не специфика Web Workers. То же самое с `fetch`, с анимациями, с чтением файлов. Как только между «начали» и «закончили» появляется зазор, в котором интерфейс отзывчив, — нужен флаг. Иначе пользователь попадёт в этот зазор, и приложение окажется в состоянии, которое разработчик не предусматривал.

Практическое следствие для вас: когда добавите `worker.terminate()` (ваш TODO в `stateManager.js:4`), `isComputing` станет ещё нужнее — по нему будет видно, есть ли что прерывать.

## 6. Замечания к применению

1. **Зависимость от первого патча.** `resetRunData()` и многоветочный обработчик клика появляются только в `SBS_PAUSE_RESUME_FIX`. Порядок применения: сначала тот патч, потом этот.

2. **Не закрыт `worker.onerror`.** Необработанное исключение внутри воркера оставит `isComputing = true` навсегда. Дописать обработчик стоит сразу.

3. **Нет таймаута и нет отмены.** Зависший воркер = зависший интерфейс без возможности восстановления кроме перезагрузки страницы.

4. **Строка в `resetRunData()` — симптом.** С фабрикой начального состояния она была бы не нужна. Стоит рефакторить, пока полей мало.

5. **UI не отражает состояние.** Guard молча глотает клики. Минимум — `disabled` на кнопке, лучше — третий визуальный режим.

6. **`isComputing` живёт в `state`, а `isRunning`/`doneRunning` — в `SBSconfig`.** Флаги одного жизненного цикла разнесены по двум объектам. Работает, но при чтении кода приходится помнить, что где. Ваша исходная идея с единым `status` решала бы это чище.
